# Equipment Balance Patcher v0.1b

Equipment Balance Patcher is a **Skyrim Special Edition equipment auditing tool**. This milestone inventories winning WEAP/ARMO records, classifies equipment conservatively, and describes the stored statistics of confidently classified groups. It performs no balancing, anomaly detection, power scoring, or game-record changes.

## Run through Synthesis

1. Build with .NET 10, or add this solution as a **Local Solution** patcher in Synthesis. The executable project is `EquipmentBalancePatcher/EquipmentBalancePatcher.csproj`. For Git import, open Synthesis, select a group and double-click the root `EquipmentBalancePatcher.synth` file.
2. Select the intended Skyrim SE profile/load order. Launch Synthesis through MO2 when its virtual filesystem is required.
3. In this patcher's autogenerated settings, set `OutputDirectory` if needed. The default is `Reports` under Synthesis's patcher-specific supplemental settings-data folder. Relative paths use that folder. If Synthesis supplies no supplemental folder (for example, standalone execution), the fallback is `%LOCALAPPDATA%/EquipmentBalancePatcher/Reports`. Absolute paths are supported.
4. Run the patcher and read its console summary. The summary lists absolute paths for all five reports, followed by lifecycle completion messages.

**Synthesis completion limitation:** the runner tagged 0.36.6 can leave a no-export patcher's GUI row/timer in Started even after its executable exits successfully. It emits the GUI success event only when an expected output plugin exists. The auditor's CLI pipeline and separate executable return normally with code 0 in integration tests. No dummy ESP or forced exit is used. See [completion investigation and direct CLI workaround](docs/SynthesisCompletion.md). The copied report's library version does not identify the user's installed GUI version.

The entry point uses `PatcherPreferences.NoPatch = true` in pinned Synthesis 0.36.6. Synthesis loads the audit's inputs read-only and skips this patcher's plugin export. Production code never accesses `PatchMod`, creates overrides, or calls a plugin writer. `EBP.esp` is only the framework's standalone identifying name; this auditor does not export it. Other patchers in the same Synthesis group can still create that group's plugin. Place the auditor after relevant equipment patchers to inspect their preceding pipeline result.

The only output replacements are the five report filenames below. Junction/symlink report directories and existing symlink destinations are rejected. Reports are staged before publication, then replaced individually. Cancellation before publication preserves existing reports. A filesystem failure during replacement can leave a mixed report set; the run fails rather than reporting success. No multi-file transaction is claimed.

## Classification and eligibility

`EquipmentReader` enumerates winning weapons and armor once, including deleted winners, and extracts application-owned snapshots. `EquipmentClassifier`, `InventoryAudit`, and `ReportWriter` use those snapshots rather than live records. Defining plugin comes from FormKey; winning plugin comes from the winning record context. Keywords are resolved through a cached LinkCache lookup. Null/unresolved references remain explicit.

Base-game/DLC canonical category and material FormKeys in `KeywordCatalog.cs` were reviewed against the locally installed **Mutagen.Bethesda.FormKeys.SkyrimSE 3.4.0** catalog. New Creation Club, Orcish Scaled and unrelated-keyword identities were reviewed against resolved links and representative snapshots in the supplied audit. That package is not added as a dependency. Keyword EditorIDs are explanatory, not matching keys. Material is never inferred from stats, names, or models. Material groups remain distinct; materialFamily/materialVariant are additional metadata and never merge groups. Reviewed base/variant pairs choose the specific tier (OrcishScaled, ElvenGilded, IronBanded, ImperialStudded), while contradictory sibling tiers remain conflicting. Silver Armor genuinely lacks material keywords in this dataset and remains unknown. See [report review and mapping provenance](docs/AuditReview.md).

Weapon animation identifies ordinary dagger, sword, war axe, mace, greatsword, bow, and crossbow categories when recognized keywords and the declared skill do not conflict. `TwoHandAxe` requires a canonical battleaxe or warhammer keyword. A crossbow animation can coexist with the canonical bow keyword. Custom rapier/spear/pike/halberd/quarterstaff/trident/glaive/scythe/OCF polearm hints withhold ordinary classification; they never establish a new category. Unreviewed material-specific keywords withhold confidence even alongside a reviewed material. Missing/conflicting material preserves a known subtype but makes overall classification partial.

Armor uses body-template armor type and slot masks, checked against recognized category/type keywords and shield flags. Reviewed profiles are head with optional hair/long-hair/circlet/ears slots, body, hands with optional forearms, feet with optional calves, and shield. Hair + circlet without head is accepted only with canonical ArmorHelmet and heavy/light structure. Combined primary slots and other masks remain unclassified; ratings are never divided or distributed across slots. Heavy armor, light armor, and clothing remain distinct.

Classification status remains `Confident`, `Partial`, or `Unclassified`. Scope is separate: `OrdinaryEquipment`, `ExpectedOutOfScope`, or `UnsupportedEquipment`, with scope reasons. Nonplayable equipment, Clothing, reviewed jewelry and Staff animation are expected exclusions from ordinary distributions/analysis; no skin, cosmetic or custom subtype is guessed. Eligibility is also separate:

| Flag | Meaning |
| --- | --- |
| `inventoryStatisticsEligible` | Confidently classified, nondeleted, nontemplated record outside expected exclusions. Describes stored fields, including enchanted/scripted/special records when otherwise eligible. Nonplayable and clothing records formerly included in some distributions are now excluded. |
| `baselineEligible` | Candidate for a future ordinary unenchanted baseline. Also excludes unknown playability, scripts, unresolved links, known artifact/bound/special flags, and malformed/missing weapon structure. No baseline comparison occurs in v0.1b. |
| `analysisEligible` | Candidate for a future ordinary comparison. Same conservative exclusions as baseline eligibility, but enchantment alone does not disqualify it. |

Each flag has its own reason-code array. JSON's eligibilitySummary counts reasons by stage and record type and labels expected/unsupported/missing/template/special reasons. Counts overlap: never sum them as mutually exclusive totals. Enchanted items can be confidently classified and included in separate descriptive groups without supplying an ordinary baseline. Templated records show their direct template reference and stored stats (`statSemantics: StoredRecord`); the auditor never follows inheritance or evaluates effective stats. Deleted records remain in inventory and diagnostics, never in distributions. Template/script restrictions remain intact.

Keyword relevance has four resolved categories: RecognizedClassification, RecognizedUnrelated, PotentialClassification and OtherUnknown. Unresolved identities remain explicit. Reviewed unrelated and other unknown keywords create no per-record classification warning; all remain in raw inventory and the aggregate keyword report. Potential classification names create a review warning, without assigning a mapping. Unknown material/subtype hints can conservatively withhold confidence/category. Unresolved keyword evidence also withholds confidence. Broken equipment/enchantment/template links remain warnings and prevent ordinary eligibility.

Diagnostics now carry severity and relevance. Expected exclusions/template/script notices are Info; missing/conflicting/unsupported evidence remains Warning. Expected exclusions suppress generic missing-material/unsupported-slot/unsupported-animation warnings, but retain those codes in raw classificationReasons. This separates expected omissions from actual review work without deleting raw data.

## Reports and schema

All files use UTF-8 without BOM, LF newlines, stable ordering, and invariant numeric formatting. Canonical JSON has no timestamp, duration, random identifier, or absolute run-dependent output path unless explicitly configured in settings. Identical input record contents, ordered load order, settings, and library versions produce identical report contents. Names are requested in English; unavailable English text stays null. JSON null and an empty CSV scalar cell mean unavailable, not zero. Array/object CSV cells contain compact JSON with CSV escaping.

| File | Row / top-level schema |
| --- | --- |
| `equipment-inventory.csv` | One row per winning record. Identity/provenance; deleted/playable flags; category/material/status/handedness; armor type/slot mask/shield flag; animation/skill; damage/speed/reach/critical damage/stagger/armor rating/weight/value; enchantment/template/equipment-type links and resolution status; keywords/flags/evidence/reasons; three eligibility flags and their reasons; diagnostics. The first row names every column. |
| `equipment-groups.csv` | One row per group **and metric**: recordType, category, armorType, material, enchanted, count, baselineEligibleCount, baselineExcludedCount, metric, availableCount, missingCount, minimum, maximum, mean, median. |
| `classification-issues.csv` | One row per record diagnostic: existing identity/code/message columns plus severity and relevance. These are classification/data diagnostics, not balance findings. |
| `keyword-summary.csv` | One row per keyword FormKey: EditorIDs, resolution statuses, relevance category, relevance hint, distinct affected-record count, record types, equipment origin/winning plugins and up to five deterministic example records. Includes recognized and unknown keywords. |
| `audit.json` | schemaVersion (`2`), patcherVersion (`0.1b`), classificationVersion (`2`), existing metadata/summary/equipment/groups/classificationDiagnostics, plus keywordSummary and eligibilitySummary. Each equipment entry retains snapshot, classification, eligibility, diagnostics. |

Schema 2 appends materialFamily, materialVariant, scope, scopeReasonsJson and statSemantics to inventory CSV; existing columns stay in order. JSON adds those classification/snapshot fields and diagnostic severity/relevance. Group CSV is unchanged and still groups by specific material. Consumers must accept schema 2 and the additional columns; raw fields have not been replaced with effective/template values.

Groups use weapon subtype/material/enchantment or armor type/slot category/material/enchantment. Normal ancillary slots share the approved primary category. Each group's `count` counts statistical members; per-metric availability may be lower. All-missing metrics have null min/max/mean/median. Baseline counts describe eligibility within that descriptive group; the overall summary also counts exclusions across the complete inventory.

The JSON load-order array preserves the effective Synthesis state order (including its read-only preceding pipeline input or empty framework identifying mod). It identifies plugin names and enabled status, not hashes of plugin files. Category/material breakdowns include all inventoried records, including deleted records; summary classification counts and distribution eligibility are separate.

## Limitations and next milestone

- Stats are stored record fields, not in-game damage, DPS, effective armor, enchantment power, or animation behavior.
- Missing weapon subrecords and nonfinite numeric fields are reported explicitly. Nonfinite values serialize as null with a diagnostic; negative stored values remain visible with a data-quality diagnostic.
- Exact material keywords can be misused by a mod. There is no universal quest/unique flag. Known artifact keywords are excluded, but unknown special items can still appear as ordinary candidates.
- Custom weapon semantics without identifiable custom keyword hints may resemble a standard engine subtype. Review custom weapon reports before using them for future comparisons.
- The slot/material catalog is deliberately limited. Accessories, clothing, nonplayable equipment, unusual armor, and unsupported subtypes remain visible without guessed classification. Expected scope exclusions do not require an ordinary material to be correctly excluded.
- No COBJ, leveled-list, merchant, official-baseline, or override-history analysis is included.
- Input parse/load failures and report initialization/write failures are genuine errors. Classification uncertainty does not abort the inventory.

The [template investigation](docs/TemplateInvestigation.md) documents stored versus proposed effective fields, actual record examples, relevant Mutagen APIs, chain failure handling, a resolver design and validation gates. Full inheritance is future work. The next milestone should validate a template resolver with per-field provenance and review resulting coverage before considering anomaly detection or balancing.

## Build and automated tests

Production dependencies remain pinned to Mutagen Skyrim **0.54.4** and Synthesis **0.36.6**. Tests use MSTest with cached versions compatible with .NET 10.

```powershell
dotnet restore "Equipment Balance Patcher.sln" -m:1
dotnet build "Equipment Balance Patcher.sln" --no-restore -m:1
dotnet test "Equipment Balance Patcher.sln" --no-restore -m:1
```

Tests retain v0.1a protections and extend material variants/conflicts, unrelated-keyword suppression, distinct-record keyword aggregation, expected exclusions, custom subtype boundaries, overlapping eligibility reasons and schema 2 determinism. Integration tests create synthetic plugin fixtures in temporary directories, invoke the pinned CLI pipeline and actual executable with a completion timeout, and verify code 0, no new ESP, preserved existing output bytes/write time, unchanged input bytes and all five reports. A differing-child/parent fixture proves raw extraction does not flatten templates. Fixture creation is test setup, not audit behavior.

For optional offline report comparison (no plugins loaded):

```powershell
dotnet run --project tools/ReplayAudit/ReplayAudit.csproj -- Reports/audit.json Reports-v0.1b
```

The copied reference reports remain in Reports; replay writes to a separate directory. [First audit review](docs/AuditReview.md) records the measured changes and limits of that comparison. Automated tests do not depend on this full dataset.

NuGet vulnerability metadata may be unavailable on an offline/restricted host (`NU1900`). The pinned Noggog/Synthesis source generator may emit an `AssemblyVersions` type-conflict warning (`CS0436`); this does not prevent the build. Neither warning establishes a failed functional check.

## Manual validation on your actual load order

1. Run this auditor in an isolated Synthesis group under your normal mod-manager environment, using a dedicated report directory. Record hashes of your input plugins and any existing group output beforehand.
2. Confirm the five reports, schema 2, intended input order, both completion messages and successful process exit. If the GUI row keeps timing, use the documented direct CLI workaround and capture the installed GUI version/log. No new EBP ESP should appear; existing output must retain its hash.
3. In xEdit, compare a normal sword, battleaxe, warhammer, bow/crossbow, heavy/light armor, helmet with hair slots, enchanted item, and mod-added item against inventory identity, winner, keywords, stats, and eligibility.
4. Review keyword-summary and eligibilitySummary without summing overlapping reason counts. Compare Golden Saint, Orcish Scaled, Silver Armor with no material, hair/circlet and ears helmets, clothing/jewelry, nonplayable DF equipment and RFM staff-animation spears against xEdit. Confirm templates report stored fields only and remain excluded.
5. Run again without changing inputs/settings and compare all five reports byte-for-byte. Check keyword affected-record counts and example identities.
6. Run after relevant equipment patchers and check that their preceding winning records are observed. Distinguish other patchers' output from this auditor's zero-export behavior.

These steps still require your real Skyrim load order. Synthetic integration tests do not constitute in-game validation.
