# Equipment Balance Patcher v0.1h

Equipment Balance Patcher is a **Skyrim Special Edition equipment auditing tool**. It inventories winning WEAP/ARMO records, classifies equipment conservatively, and describes stored statistics. v0.1h prints a ranked ordinary-weapon base-damage review report directly in the Synthesis console and saves the same findings to `WeaponDryRun.txt`. The v0.1g evidence rules, v0.1f canonical comparison and v0.1e statistical analyzer remain unchanged. It performs no automatic balancing, power scoring, or game-record changes. See [dry-run findings and ranking](docs/WeaponDryRun.md), [weapon evidence](docs/WeaponEvidenceAudit.md), [reference comparisons](docs/ReferenceComparison.md) and [statistical methods](docs/BalanceAudit.md).

v0.1c adds a separate read-only template-chain prototype: proposed field values, provenance and hypothetical classification scenarios remain unvalidated and do not change production results. The long-term goal is relative consistency among comparable equipment within the load order, preserving material tiers and intentional exceptions. Global combat difficulty/formulas and editable vanilla scaling tables are outside this milestone. See [prototype policies, results and validation](docs/TemplatePrototype.md).

The [v0.1d template semantics research](docs/TemplateSemanticsValidation.md) provides source-backed field matrices, keyword hypotheses and reproducible CK/runtime tests. No inheritance policy was promoted: controlled validation remains required before any effective-value implementation. Comparisons and ordinary evidence inspection exclude all templates. The executable is now v0.1h; JSON schema remains 6.

The available audit replay resolves all 28 references and matches 140 of 825 eligible records, including the 28 references themselves. **112 other records** become comparable, versus 91 statistically supported records in v0.1e; 70 of those 112 lack statistical support. Seventy-five records exceed a reference tolerance, with substantial author-intent and special-item caveats. This is a modest coverage improvement and a useful review companion, not a replacement for peer analysis. The available dataset does not contain `RFM - Balance Patch.esp`.

The independent weapon evidence view inspects **391** ordinary-scope records: 86 have matching keyword/name evidence, 283 have keyword-only evidence, and 22 have neither reviewed keyword evidence nor a recognized material word. There are no ordinary material conflicts in this dataset. Sixty-eight have usable references, including 16 self-references; 49 exceed a numerical tolerance. All five previously eligible RFM weapons remain inspectable and its 297 excluded weapons remain outside this view. Crafting/tempering extraction is deferred because the stored dataset contains no COBJ evidence; its value is unmeasured. Names and local scope hints never change production classification or eligibility.

The new damage shortlist contains **10 higher** and **7 lower** candidates among **52 non-reference weapons compared**. Only existing Damage tolerance findings qualify; other metric deviations stay in detailed reports. Each direction shows up to ten candidates ranked by existing percentage difference, with canonical provenance and structural warnings. Skyforge variants and SRE Golden equipment illustrate why these are review candidates, not confirmed balance errors. No-reference records remain unassessed. Undefined percentages are shown separately, never fabricated or mixed into percentage rankings.

## Run through Synthesis

1. Build with .NET 10, or add this solution as a **Local Solution** patcher in Synthesis. The executable project is `EquipmentBalancePatcher/EquipmentBalancePatcher.csproj`. For Git import, open Synthesis, select a group and double-click the root `EquipmentBalancePatcher.synth` file.
2. Select the intended Skyrim SE profile/load order. Launch Synthesis through MO2 when its virtual filesystem is required.
3. In this patcher's autogenerated settings, set `OutputDirectory` if needed. The default is `Reports` under Synthesis's patcher-specific supplemental settings-data folder. Relative paths use that folder. If Synthesis supplies no supplemental folder (for example, standalone execution), the fallback is `%LOCALAPPDATA%/EquipmentBalancePatcher/Reports`. Absolute paths are supported.
4. Run the patcher and read its console summary: inventory/statistical totals, report paths and the higher/lower base-damage shortlist, followed by lifecycle completion messages. The same shortlist is saved to `WeaponDryRun.txt`. `MaximumTemplateDepth` defaults to 128 parent edges and must be positive. `EnableReferenceComparison` defaults to true; comparisons share the existing per-metric `BalanceThresholds` and enchanted-candidate switch, without peer-count or MAD requirements. Evidence inspection and dry-run formatting add no settings.

**Synthesis completion limitation:** the runner tagged 0.36.6 can leave a no-export patcher's GUI row/timer in Started even after its executable exits successfully. It emits the GUI success event only when an expected output plugin exists. The auditor's CLI pipeline and separate executable return normally with code 0 in integration tests. No dummy ESP or forced exit is used. See [completion investigation and direct CLI workaround](docs/SynthesisCompletion.md). The copied report's library version does not identify the user's installed GUI version.

The entry point uses `PatcherPreferences.NoPatch = true` in pinned Synthesis 0.36.6. Synthesis loads the audit's inputs read-only and skips this patcher's plugin export. Production code never accesses `PatchMod`, creates overrides, or calls a plugin writer. `EBP.esp` is only the framework's standalone identifying name; this auditor does not export it. Other patchers in the same Synthesis group can still create that group's plugin. Place the auditor after relevant equipment patchers to inspect their preceding pipeline result.

The only output replacements are the eleven report filenames below. Junction/symlink report directories and existing symlink destinations are rejected. Reports are staged before publication, then replaced individually. Cancellation before publication preserves existing reports. A filesystem failure during replacement can leave a mixed report set; the run fails rather than reporting success. No multi-file transaction is claimed.

## Classification and eligibility

`EquipmentReader` enumerates winning weapons and armor once, including deleted winners, and extracts application-owned snapshots. `EquipmentClassifier`, `InventoryAudit`, and `ReportWriter` use those snapshots rather than live records. Defining plugin comes from FormKey; winning plugin comes from the winning record context. Keywords are resolved through a cached LinkCache lookup. Null/unresolved references remain explicit.

Base-game/DLC canonical category and material FormKeys in `KeywordCatalog.cs` were reviewed against the locally installed **Mutagen.Bethesda.FormKeys.SkyrimSE 3.4.0** catalog. New Creation Club, Orcish Scaled and unrelated-keyword identities were reviewed against resolved links and representative snapshots in the supplied audit. That package is not added as a dependency. Keyword EditorIDs are explanatory, not matching keys. Material is never inferred from stats, names, or models. Material groups remain distinct; materialFamily/materialVariant are additional metadata and never merge groups. Reviewed base/variant pairs choose the specific tier (OrcishScaled, ElvenGilded, IronBanded, ImperialStudded), while contradictory sibling tiers remain conflicting. Silver Armor genuinely lacks material keywords in this dataset and remains unknown. See [report review and mapping provenance](docs/AuditReview.md).

Weapon animation identifies ordinary dagger, sword, war axe, mace, greatsword, bow, and crossbow categories when recognized keywords and the declared skill do not conflict. `TwoHandAxe` requires a canonical battleaxe or warhammer keyword. A crossbow animation can coexist with the canonical bow keyword. Custom rapier/spear/pike/halberd/quarterstaff/trident/glaive/scythe/OCF polearm hints withhold ordinary classification; they never establish a new category. Unreviewed material-specific keywords withhold confidence even alongside a reviewed material. Missing/conflicting material preserves a known subtype but makes overall classification partial.

Armor uses body-template armor type and slot masks, checked against recognized category/type keywords and shield flags. Reviewed profiles are head with optional hair/long-hair/circlet/ears slots, body, hands with optional forearms, feet with optional calves, and shield. Hair + circlet without head is accepted only with canonical ArmorHelmet and heavy/light structure. Combined primary slots and other masks remain unclassified; ratings are never divided or distributed across slots. Heavy armor, light armor, and clothing remain distinct.

Classification status remains `Confident`, `Partial`, or `Unclassified`. Scope is separate: `OrdinaryEquipment`, `ExpectedOutOfScope`, or `UnsupportedEquipment`, with scope reasons. Nonplayable equipment, Clothing, reviewed jewelry and Staff animation are expected exclusions from ordinary distributions/analysis; no skin, cosmetic or custom subtype is guessed. Eligibility is also separate:

| Flag | Meaning |
| --- | --- |
| `inventoryStatisticsEligible` | Confidently classified, nondeleted, nontemplated record outside expected exclusions. Describes stored fields, including enchanted/scripted/special records when otherwise eligible. Nonplayable and clothing records formerly included in some distributions are now excluded. |
| `baselineEligible` | Candidate for the ordinary unenchanted balance reference population. Also excludes unknown playability, scripts, unresolved links, known artifact/bound/special flags, and malformed/missing weapon structure. Balance comparisons additionally require sufficient valid independent peers. |
| `analysisEligible` | Candidate for ordinary balance comparison. Same conservative exclusions as baseline eligibility, but enchantment alone does not disqualify it. |

Each flag has its own reason-code array. JSON's eligibilitySummary counts reasons by stage and record type and labels expected/unsupported/missing/template/special reasons. Counts overlap: never sum them as mutually exclusive totals. Enchanted items can be confidently classified and included in separate descriptive groups without supplying an ordinary baseline. Production templated records retain their direct reference and stored stats (`statSemantics: StoredRecord`). The separate investigation traverses chains and proposes values; it does not establish effective engine stats or promote eligibility. Deleted records remain in inventory and diagnostics, never in distributions. Template/script restrictions remain intact.

Keyword relevance has four resolved categories: RecognizedClassification, RecognizedUnrelated, PotentialClassification and OtherUnknown. Unresolved identities remain explicit. Reviewed unrelated and other unknown keywords create no per-record classification warning; all remain in raw inventory and the aggregate keyword report. Potential classification names create a review warning, without assigning a mapping. Unknown material/subtype hints can conservatively withhold confidence/category. Unresolved keyword evidence also withholds confidence. Broken equipment/enchantment/template links remain warnings and prevent ordinary eligibility.

Diagnostics now carry severity and relevance. Expected exclusions/template/script notices are Info; missing/conflicting/unsupported evidence remains Warning. Expected exclusions suppress generic missing-material/unsupported-slot/unsupported-animation warnings, but retain those codes in raw classificationReasons. This separates expected omissions from actual review work without deleting raw data.

## Reports and schema

All files use UTF-8 without BOM, LF newlines, stable ordering, and invariant numeric formatting. Canonical JSON has no timestamp, duration, random identifier, or absolute run-dependent output path unless explicitly configured in settings. Identical input record contents, ordered load order, settings, and library versions produce identical report contents. Names are requested in English; unavailable English text stays null. JSON null and an empty CSV scalar cell mean unavailable, not zero. Array/object CSV cells contain compact JSON with CSV escaping.

| File | Row / top-level schema |
| --- | --- |
| `equipment-inventory.csv` | One row per winning record. Identity/provenance; deleted/playable flags; category/material/status/handedness; armor type/slot mask/shield flag; animation/skill; damage/speed/reach/critical damage/stagger/armor rating/weight/value; enchantment/template/equipment-type links and resolution status; keywords/flags/evidence/reasons; three eligibility flags and their reasons; diagnostics. The first row names every column. |
| `equipment-groups.csv` | One row per group **and metric**: recordType, category, armorType, material, enchanted, count, baselineEligibleCount, baselineExcludedCount, metric, availableCount, missingCount, minimum, maximum, mean, median. |
| `classification-issues.csv` | One row per record diagnostic: existing identity/code/message columns plus severity and relevance. These are classification/data diagnostics, not balance findings. |
| `keyword-summary.csv` | One row per keyword FormKey: EditorIDs, resolution statuses, relevance category, relevance hint, distinct affected-record count, record types, equipment origin/winning plugins and up to five deterministic example records. Includes recognized and unknown keywords. |
| `template-analysis.csv` | One row per templated child and field: child identity, direct/root parent, depth/status, raw/proposed JSON values, source FormKey/winner, rule, resolution/validation status, nullable difference and diagnostics. No chain structure is duplicated per field. |
| `balance-findings.csv` | One row per provisional metric finding, with identity/winner, peer keys/count/range/median/MAD, differences, optional percentage/robust score, evidence class and false-positive reasons. |
| `balance-groups.csv` | One row per structural/material cohort and metric: membership, reference design IDs, distributions/quartiles/MAD, origin/winner concentration, duplicate warnings and sufficiency. |
| `reference-comparisons.csv` | One row per compared metric, or one status row for eligible NoReference/ReferenceUnavailable records. Candidate and canonical identities, both winning plugins, canonical/winning reference names, values, signed/absolute/percentage differences, metric/record status and uncertainty reasons. Excluded records remain in JSON only. |
| `weapon-evidence.csv` | One row per winning weapon, including exclusions: identity, subtype/animation/special flags, existing eligibility, material keyword identities/tiers, whole-word name evidence, agreement/confidence, uncertainty, crafting deferral and optional existing reference identity/winner/metric comparisons. No name-based material assignment. |
| `WeaponDryRun.txt` | The same ordinary-weapon damage review block printed in the console: precise coverage, up to ten higher/lower candidates, source/reference winners and structural notes, plus material evidence summary. Undefined percentages have a separate unranked section when needed. |
| `audit.json` | schemaVersion (`6`), patcherVersion (`0.1h`), classificationVersion (`2`), existing metadata/summary/equipment/groups/diagnostics and keyword/eligibility summaries, plus templatePolicyVersion, templateAnalysis, templateRoots, balanceAnalysis, referenceAnalysis and compact weaponEvidenceAnalysis policy/summary. Chains are stored once per templated child; hypothetical outcomes remain separate. |

Schema 2 appends materialFamily, materialVariant, scope, scopeReasonsJson and statSemantics to inventory CSV; existing columns stay in order. JSON adds those classification/snapshot fields and diagnostic severity/relevance. Group CSV is unchanged and still groups by specific material. Consumers must accept schema 2 and the additional columns; raw fields have not been replaced with effective/template values.

Schema 3 retains all four existing CSV formats and raw JSON equipment entries unchanged. It adds the template investigation objects and settings.MaximumTemplateDepth, and bumps only patcher/report versions. Classification version remains 2. Template field policies are `prototype-1`; ProposedInherited does not mean ValidatedInherited. RootReplacement, ChildKeywords and ChainKeywordUnion compare unvalidated alternatives in JSON. Their possible future eligibility flags never feed production statistics or baselines. Shared-root summaries describe potential duplicate sampling; they create no actual baseline.

Schema 4 adds `balanceAnalysis` and balance settings, plus two CSVs. All five earlier CSV schemas and contents remain unchanged for identical inputs. Existing JSON equipment, classification, eligibility, groups and template objects retain their contents. Balance policy `stored-independent-1` uses exact specific material tiers and structural cohorts, unenchanted references, self-exclusion and conservative evidence gates. JSON includes every candidate's metric assessment and every record's exclusion status, even when no finding is emitted. [Method and limitations](docs/BalanceAudit.md) explain zero MAD, sampling and the limited descriptive progression comparison.

Schema 5 adds `referenceAnalysis` and one CSV plus `EnableReferenceComparison`. All seven existing CSVs and the complete JSON statistical analysis remain unchanged for identical inputs. Reference policy `winning-canonical-1` uses exact category/material/armor-type matches and a reviewed explicit FormKey catalog; canonical identity and current winner are distinct. JSON includes resolution failures, excluded records and full coverage by category/tier. [Reference documentation](docs/ReferenceComparison.md) explains counting, tolerances, self-references, real deviations and limitations. Replay accepts schemas 1–5.

Schema 6 adds the evidence CSV and concise `weaponEvidenceAnalysis` policy/summary, without new settings. All eight prior CSVs and existing JSON analysis objects remain unchanged. Evidence policy `ordinary-keyword-name-1` permits material-uncertain records for inspection only, retains special/custom restrictions, and reuses existing numerical comparisons without modifying them. Names remain weak evidence; crafting is explicitly not extracted. Per-weapon evidence is in the CSV, avoiding a second copy in JSON. Replay accepts schemas 1–6.

v0.1h adds only the text report and console formatting. Schema 6, every prior JSON analysis object and all nine CSVs remain unchanged; only patcherVersion becomes 0.1h. Ranking uses stored results with a constant ten-entry display limit, not a new analysis algorithm. [Dry-run documentation](docs/WeaponDryRun.md) records actual top findings, coverage, remaining false-positive risks and reproducibility checks.

Groups use weapon subtype/material/enchantment or armor type/slot category/material/enchantment. Normal ancillary slots share the approved primary category. Each group's `count` counts statistical members; per-metric availability may be lower. All-missing metrics have null min/max/mean/median. Baseline counts describe eligibility within that descriptive group; the overall summary also counts exclusions across the complete inventory.

The JSON load-order array preserves the effective Synthesis state order (including its read-only preceding pipeline input or empty framework identifying mod). It identifies plugin names and enabled status, not hashes of plugin files. Category/material breakdowns include all inventoried records, including deleted records; summary classification counts and distribution eligibility are separate.

## Limitations and next milestone

- Stats are stored record fields, not in-game damage, DPS, effective armor, enchantment power, or animation behavior.
- Missing weapon subrecords and nonfinite numeric fields are reported explicitly. Nonfinite values serialize as null with a diagnostic; negative stored values remain visible with a data-quality diagnostic.
- Exact material keywords can be misused by a mod. There is no universal quest/unique flag. Known artifact keywords are excluded, but unknown special items can still appear as ordinary candidates.
- Custom weapon semantics without identifiable custom keyword hints may resemble a standard engine subtype. Review custom weapon reports before using them for future comparisons.
- The slot/material catalog is deliberately limited. Accessories, clothing, nonplayable equipment, unusual armor, and unsupported subtypes remain visible without guessed classification. Expected scope exclusions do not require an ordinary material to be correctly excluded.
- No COBJ, leveled-list, merchant or override-history analysis is included. Canonical comparisons use selected current winners, not untouched vanilla stats or an engine-validated balance standard.
- Input parse/load failures and report initialization/write failures are genuine errors. Classification uncertainty does not abort the inventory.

The original [template investigation](docs/TemplateInvestigation.md) documents the architecture that led to v0.1c. The [implemented prototype](docs/TemplatePrototype.md) now resolves chains with per-field provenance and reports potential classification changes. Engine-validated inheritance remains future work. The [independent balance audit](docs/BalanceAudit.md) uses only stored eligible records; it introduces no inherited substitutions. Review its real findings and calibrate thresholds before authorizing stat changes. Template engine validation remains a separate prerequisite for future template comparisons.

```powershell
dotnet restore "Equipment Balance Patcher.sln" -m:1
dotnet build "Equipment Balance Patcher.sln" --no-restore -m:1
dotnet test "Equipment Balance Patcher.sln" --no-restore -m:1
```
